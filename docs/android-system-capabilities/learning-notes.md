# 学习记录与待验证问题

[学习目录](README.md)

这里记录理解是否连贯，以及未来需要哪些证据。下列设备观察均是**待做项目，尚未运行**；不是要求现在开始开发或部署。

## 理解练习

先尝试自己解释，再展开参考答案。这里检查的是概念之间的关系，不要求记住类名。

**1. 我想让现有桌面显示“14:00 项目会议”，需要开发 Launcher 吗？**

<details>
<summary>参考答案</summary>

通常先研究日程小组件，由用户原有的 Launcher 承载。只有希望自己组织整个主屏幕时，才需要考虑 Launcher。见[第一章](01-capability-map.md)。

</details>

**2. 我的 Launcher 能画一块日程区域，是不是已经能接纳别的 App 的天气小组件？**

<details>
<summary>参考答案</summary>

不是。自己的区域可以由自己的 UI 绘制；接纳别的 App 提供的组件，还需要实现小组件宿主的绑定、摆放、尺寸和更新接收等工作。见[第二章](02-launcher.md)。

</details>

**3. 关掉壁纸设置页面后，为什么背景还会动？**

<details>
<summary>参考答案</summary>

设置页面负责配置，系统通过单独的壁纸入口调用绘制。预览时就可能开始绘制；是否继续画，取决于可见性和绘制区域等生命周期条件。见[第三章](03-live-wallpapers.md)。

</details>

**4. App 里已经变成“15:00”，桌面为什么还可能显示“14:00”？**

<details>
<summary>参考答案</summary>

取得并保存新数据，与向宿主提交新卡片内容，是不同步骤。App 还需要完成小组件更新；旧内容可以先留在桌面上。见[第四章](04-app-widgets.md)和[第五章](05-data-and-lifecycle.md)。

</details>

**5. 用户清除“会议改期”的通知后，会议会变回 14:00 吗？**

<details>
<summary>参考答案</summary>

不会。会议时间是业务数据，通知只是围绕它发出的提醒。清除这张通知通常只是移除显示；如果产品另外实现了业务操作，应按那个操作的含义判断。见[第五章](05-data-and-lifecycle.md)。

</details>

**6. 音乐控制、外卖进度和日程都像锁屏卡片，可以用同一个小组件接口实现吗？**

<details>
<summary>参考答案</summary>

不能仅凭外观作这个判断。音乐控制通常需要媒体会话，外卖跟踪可涉及更新通知或 Live Updates，日程区域可能是锁屏小组件，也可能是厂商内置功能。需要辨认功能和接入机制，同一内容也可以有多种呈现。见[第六章](06-lock-screen-cards.md)。

</details>

## 未来设备观察：先记录环境，再解释现象

同一观察至少记录手机型号、Android 版本、系统构建版本、Launcher 名称和版本、App 版本及相关电池设置。个人或小范围验证可以按现有手机做，无需先覆盖整个 Android 市场。

| 板块 | 想验证的问题 | 应记录的证据 |
|---|---|---|
| Launcher | 用户如何选择和切回默认桌面？ | 系统入口、选择结果、实际 Home 行为 |
| Launcher 宿主 | 绑定和调整小组件尺寸时怎样与提供者交互？ | 实例 ID、配置流程、尺寸回调与实际布局 |
| 动态壁纸 | 预览与正在使用是否同时产生引擎？ | 每个 Engine 的独立标识与生命周期日志 |
| 动态壁纸 | 打开全屏页、锁屏后何时停止绘制？ | 可见性、表面回调、实际绘制次数，避免仅凭截图推断耗电 |
| 动态壁纸 | 系统允许选哪些主屏幕与锁屏组合？ | 选择器选项与实际显示，按设备分别记录 |
| 小组件 | 本地数据变化后，显式更新前后有什么差别？ | 数据版本、提交时刻、可观察的卡片内容 |
| 小组件 | 系统回收进程后，已有显示与后续更新怎样恢复？ | 回收方式、进程重建日志、持久配置与卡片内容 |
| 小组件 | 放置两个实例时，配置和点击目标是否独立？ | 实例配置、目标 ID、分别调整尺寸后的结果 |
| 锁屏 | 通知、播放控制或任务跟踪实际出现在哪里？ | 手机与系统版本、用户设置、展示入口，以及可观察的更新结果 |
| 多入口 | 同一事件到达、保存、更新和打开相隔多久？ | 分阶段时间与可观察状态，不以“发送成功”代替最终结果 |

系统回收、划掉最近任务和强行停止应分别记录，不能统称“杀后台”。测试过程也应区分实际设备观察与模拟出来的状态。

## 后续源码调研应回答什么

还没有为桌面、壁纸、小组件及新加入的锁屏能力选定完整的开源案例。选择时先看它能否清楚展示我们要理解的机制：

- Launcher：怎样保存桌面布局、监听应用入口变化、绑定与删除小组件？
- 动态壁纸：怎样隔离不同 Engine 的资源，处理不可见和 Surface 销毁？
- 小组件：怎样持久化每个实例的配置，串起数据同步、更新与点击目标？
- 锁屏：怎样维护媒体会话或当前任务状态，区分请求展示与实际展示？

将来引用代码时记录仓库、提交版本、关键文件和许可证，并把“从源码看到的行为”与“实机验证的行为”分开。当前不把任何项目写成已经审计通过的推荐。

## 讨论中的产品问题

这些问题留给需求讨论，不影响现在继续学领域知识：

- 最希望用户在主屏幕上直接得到的是信息、操作入口，还是一种视觉氛围？
- 桌面指的是给现有 Launcher 增加内容，还是最终想自己组织整个主屏幕？
- 内容允许有多旧，哪些事件值得打断用户，哪些只需要安静更新？
- 哪些内容可以在未解锁时显示，点击后需要怎样恢复登录与详情？

先通过手册理解这些选择会改变什么，再决定产品组合及协议。
