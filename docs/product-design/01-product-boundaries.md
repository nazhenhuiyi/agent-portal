# 01 · 产品目标与边界

[设计目录](README.md)

状态：**产品职责与 App 内部范围已按用户反馈收紧，其余实现建议待讨论**。更新日期：2026-09-08。

## 我们要提供什么

**接收业务方提供的数据，通过手机小组件、通知和历史记录进行展示，并按配置提供跳转入口。** 云端 Agent 的状态与关键任务是首个使用场景。

这个产品包含服务端和原生客户端。Agent、脚本、定时任务是使用方，只需对接我们的服务。它们不需要分别处理 Android 小组件、手机推送渠道或客户端连接。

这里的“云端 Agent”也可以运行在用户自己的电脑上。“云端”描述的是手机之外的运行位置，并不要求一开始购买云服务器。

用户已经明确的方向：

- 同一个仓库包含服务端和原生客户端，先做 Android，iOS 之后考虑；不用 React Native、Flutter 等跨平台客户端方案。
- App 内部保持非常简洁，只保留必要的设置、配置和历史数据展示。
- 小组件和通知是核心展示方式；详情通过业务方配置的链接跳转。
- 我们是数据展示方。网站的生成、托管、内容和可用性属于业务方职责，明确不在本产品范围内。
- 希望通过 Agent 配置模板，支持更丰富的组合和动态展示。
- 借鉴 ntfy 的设计，自行实现服务端与原生客户端，让产品代码的规模、结构和行为保持在自己可理解、可维护的范围内。

上述是已确认的边界。下文对具体展示行为、数据组织和实现方式的描述仍属于设计建议。

## App 内部只保留少量内容

App 内部围绕两个用途组织，具体页面划分后续再定：

| 用途 | 内容 |
|---|---|
| 设置与配置 | 必要的服务连接、展示选择和通知偏好等配置；具体配置项待设计 |
| 历史数据 | 浏览已经接收的数据，查看摘要，按业务方配置的链接跳转 |

日常展示以小组件和通知为主。丰富的模板和动效服务于这些展示需求，不据此扩展出复杂的 App 首页或业务操作页面。

## 先看一天的使用过程

假设用户有一个“研究助手”，每天早上生成行业日报。

| 时刻 | Agent 一侧发生什么 | 手机上希望看到什么 |
|---|---|---|
| 08:00 | 开始整理今天的资料 | 小组件显示“研究助手：正在整理日报” |
| 08:03 | 提交日报完成状态、摘要和详情链接 | 小组件显示“今日日报已完成”与简短摘要；收到一条完成提醒 |
| 08:10 | 用户点击卡片或通知 | 按配置打开业务方提供的链接 |
| 12:00 | 没有新的任务变化 | 仍能查看今天的结果和信息更新时间 |
| 一段时间未收到更新 | 原因尚不清楚 | 保留最后已知状态，并说明最后更新时间；不能直接断言 Agent 已故障 |

不要求每次进度变化都弹通知。小组件适合承载持续信息，通知适合提醒值得注意的变化，两者可以引用同一个任务。

一个重要区别是：**清除“日报完成”的通知，不会清除日报的完成状态。** 状态必须可以独立查询和恢复，不能只存在于某一条通知里。

## 三个角色怎样分工

一次日报完成的基本关系是：

**业务方提交结果 → 我们的服务保存并安排分发 → 原生客户端取得内容并请求更新手机界面。**

用户点击后，另走一条路径：**手机打开业务方提供的详情网址。**

| 角色 | 负责什么 | 日报中的例子 |
|---|---|---|
| 业务方：Agent、脚本、定时任务 | 执行业务，产生事实，提供摘要、展示意图和详情地址 | “日报完成，摘要是……，详情在这个网址” |
| 我们的服务端 | 校验发布权限，保存状态和必要的变化记录，管理模板与订阅关系，安排分发并支持补取 | 保存今天的日报，让有权限的手机取得它 |
| 我们的原生客户端 | 接收与同步，保留本地内容，提供必要配置和历史记录，按系统能力呈现，处理点击 | 更新小组件、请求显示通知、浏览历史、打开链接 |

手机操作系统和桌面程序决定后台执行、通知显示和小组件承载的具体规则。客户端需要适配这些规则，服务端不能远程绕过它们。

Agent 和我们的服务端可以部署在同一台电脑，也可以分开部署。它们仍是两个职责：一个做业务，一个把业务结果提供给手机。

## “24 小时的窗口”具体意味着什么

建议把目标定义为：**用户随时查看时，有最后已知的状态、关键结果和明确的更新时间；系统有机会同步时，再更新到新的内容。**

这里有三个不同的问题：

| 问题 | 我们可以怎样设计 |
|---|---|
| 没打开 App，能否看到已有内容？ | 通过用户放置的小组件展示本地已保存内容；通知是否保留由系统和用户控制 |
| Agent 有变化，能否尽快看到？ | 选择适合目标手机的接收路径，结合后台同步；需要实测延迟与耗电 |
| 屏幕上的状态是否仍可信？ | 展示状态上报时间、手机同步时间；对超时未更新的信息提示不确定性 |

这不意味着屏幕始终点亮，也不意味着小组件能每秒联网刷新。后台限制、断网、用户停止 App 都会影响更新。

Agent 是否在线、任务是否失败等业务状态，由业务方提供。我们展示收到的数据及其更新时间，并说明自身的同步状态，不负责探测 Agent 或电脑是否正常运行，也不把未收到更新自行解释为业务失败。

相关机制见 [后台与连接](../push-notifications/02-connections-and-background.md) 和 [数据怎样变成界面更新](../android-system-capabilities/05-data-and-lifecycle.md)。

## 内容与展示之间，需要留出哪几条边界

### 业务内容和展示行为分开

业务方可以提交“研究助手在线”或“日报正在生成”等内容，并指定展示与提醒意图。我们负责保存、更新和呈现，不判断这些业务结论是怎样得出的。

Agent 和任务帮助我们解释使用场景，是否需要成为协议中的专门对象尚未确定。协议设计应先关注如何标识一份展示数据、更新它、保存历史，以及何时提醒。

建议服务保存可查询的当前状态，并保留用于恢复和近期浏览的变化记录。具体保存多久、是否保存全部进度，后续再定。

### 模板决定如何呈现，业务方决定发生了什么

例如业务方报告“日报完成”，并选择一个带小猫和彩虹的模板。模板决定摘要位置、配色、素材，以及在支持的位置如何播放动效。

建议模板描述客户端支持的组件、布局和状态对应的展示，不直接下发任意原生代码。这样可以调整组合和素材，同时保持客户端职责明确。

同一份内容需要适应不同展示位置：小组件受桌面承载机制限制，通知受系统样式限制，App 内历史记录保持简洁。小猫动画不可用时，仍应能看到静态图、完成状态和详情入口。

要分别看待三种更新：业务内容变了，更新数据；布局或素材变了，更新模板资源；新增客户端不认识的组件或动画机制，通常需要升级 App。不能承诺服务端改模板就能获得任意新能力。

模板是否已经缓存、素材能否下载，也会影响展示。模板失败不应阻断基本摘要和跳转。具体协议与支持范围尚未确定。小组件动画的研究边界见 [小猫吐彩虹的例子](../android-system-capabilities/04-app-widgets.md#rainbow-cat)。

### 链接是业务方提供的数据

我们负责保存链接，并在用户点击时按配置发起跳转。网站是否可访问、网页登录和网站内容由业务方处理，不作为本系统的设计或验收目标。

本产品不生成、托管或代理业务网站，也不为其提供网络隧道。这是明确的产品职责边界，不是等待后续版本补充的功能。

必要的缓存、同步和本系统的错误提示属于展示基础能力，不改变 App 内只有少量配置与历史内容的定位。

## 怎样参考 ntfy

**已确认：借鉴设计，自行实现。** ntfy 是设计与源码研究对象，不作为产品运行依赖，也不以 fork 后改造作为实现路线。

已有 [ntfy 案例研究](../push-notifications/06-ntfy-case-study.md) 记录了官方文档和固定源码版本，本轮先利用这些证据。需要确认某一实现细节时，再拉取源码对照，不把它的实现选择直接当成我们的需求。

| ntfy 中值得借鉴的设计 | 对我们的意义 |
|---|---|
| 简洁 HTTP 发布入口 | Agent 或脚本容易集成，简单场景不必强制使用 SDK |
| topic 发布与订阅 | 发送方不必逐一指定手机；我们仍需决定订阅的是 Agent、任务组还是其他对象 |
| 消息身份、缓存与断线补取 | 手机漏接后有恢复依据，也能处理重复接收 |
| 点击 URI | 内容可以引导到业务方网页，分发服务不用理解网页内部业务 |
| 认证与访问控制 | 发布和读取都有明确权限，不能把难猜的网址当作完整授权机制 |
| 多种接收路径 | 业务方使用统一入口，平台差异由我们的系统处理 |

我们的需求还需要明确：**同一份展示数据怎样持续更新、怎样保留历史，以及如何在不同展示位置使用模板呈现它。** ntfy 的主题消息和缓存机制可供参考，但不能直接当作已经设计好的展示数据模型或模板系统。

实现时只引入本产品需要的能力，不以覆盖 ntfy 全部功能为目标，也不默认要求与 ntfy API 或客户端兼容。每项借鉴都先说明它解决的问题，再决定适合我们的最小实现。

自行实现指产品的服务端与客户端逻辑；可以使用必要的基础库和平台 SDK，具体选型仍待讨论。Android 的后台执行、推送和小组件约束仍按平台规则处理。ntfy 的 [Android 接收路径](../push-notifications/06-ntfy-case-study.md#4-android-路径一直接订阅) 可以帮助理解取舍，但不直接决定我们的接收方案。

## 建议先验证的范围

首个闭环建议是：业务方提交展示数据 → 服务端保存 → Android 小组件显示最新摘要 → 按规则触发通知 → 点击按配置跳转 → App 内可查看历史，断网后重新打开能补齐数据。

Android App 内只提供必要的设置、配置与历史数据展示。先用已有手机验证个人使用场景，具体设备和接收路径仍待确定。

模板能力应纳入整体设计；首个验证可以用一个可配置模板，检验“业务上报与展示样式分开”是否成立。完整模板编辑器、丰富动画库可以在运行闭环成立后扩展。

Agent 执行、业务调度、远程操作电脑和业务网站建设不属于本产品职责。自定义 Launcher、动态壁纸建议不纳入首个版本；iOS 按已确认方向留到之后考虑。

仓库可以逐步组织为下面几个部分，当前仅列职责，不提前创建空工程：

| 目录建议 | 内容 |
|---|---|
| `server/` | 我们的服务端实现 |
| `clients/android/` | 原生 Android 工程 |
| `protocol/` | 后续确认的协议、Schema 与兼容性约定 |
| `examples/` | 业务方发布状态、任务和选择模板的最小示例 |
| `docs/` | 产品设计、领域学习和运行说明 |

底座方案继续见 [技术选型](02-foundation-stack.md)、[数据结构](03-data-model.md) 和 [API](04-api.md)。这些草案结合前台、后台执行条件和断网恢复规则设计，尚未完成实机验证。
