# 协议行为约定

[协议目录](README.md) · [API 说明](../docs/product-design/04-api.md)

本文件是 v0.2 的行为契约，补齐 JSON Schema 无法独立保证的规则。通知 Notification 与展示条目 Item 是独立资源；共用 Topic、权限、事件日志和同步游标。

## 1. 校验、默认值与精度

- HTTP JSON 请求只接受 UTF-8，拒绝重复对象键、无效 JSON、非有限数值和不成对的 Unicode 代理字符。按原始字节数先检查请求大小。
- 请求不自动把字符串转换成数值，不悄悄删除未知字段。Schema 的 `default` 是声明，服务必须显式补齐，不能依赖验证器恰好改写对象。
- Item 的缺省 `body` 为 `""`、`data` 为 `{}`；Item 写入不接受 `notify`，不触发通知。Notification 有独立 `content`，只接受 title（最多 120 码点）、body（最多 500 码点）和 link；不接受模板或 data。通知缺省 body 为 `""`、mode 为 `alert`、ttl_seconds 为 600。整份替换只移除本资源内遗漏的可选字段。
- 通知请求 `silent` 或 TTL 为 0 时，Notification 的 mode 为 silent、expires_at 为 null。其他通知为 alert，到期时间为记录时间加 TTL。TTL 是允许新提醒的期限，不是内容自动删除时间。
- 标题不能全为空白。字符串长度按 Unicode 码点计算。链接只接受有主机的 HTTP(S) URI，不允许 URL 内携带用户名密码；不探测目标网页。
- `content` 补齐默认值后，以紧凑 UTF-8 JSON 计费大小：最多 16 KiB。根 content 对象深度算 1，每进入一个属性值或数组元素加 1，最大 8。JSON 中整数必须在 JavaScript 安全整数范围内，大整数由业务方表示为字符串。
- 数据库日志序号使用 64 位整数，Node 中用 BigInt 或无损十进制字符串；它不作为 JSON number 暴露。Item 和 Notification 各自的 revision 为 1 至 9,007,199,254,740,991，耗尽时拒绝更新，绝不能回绕。
- API 时间均由服务生成，以 UTC RFC 3339 `Z` 结尾。排序依据日志序号，不能依赖机器时钟严格递增。客户端可结合响应的 `server_time` 估计偏差，判断提醒是否过期。

默认限制：普通 JSON 写入体 32 KiB，模板 JSON 64 KiB，增量与历史每页 2 MiB，全量快照 16 MiB；素材 2 MiB、每边最多 2,048 像素且必须是单帧 PNG / WebP。服务应在 capabilities 中返回实际配置，上传或读取遇到上限不得偷偷截断内容。返回的单个事件必须能放入一页。

普通写入或模板超限返回 413；格式不支持为 415；符合 JSON 但不符合字段/语义为 422。无效 JSON、重复键、条件头或查询参数格式错误为 400。未知查询参数也拒绝，避免游标拼错后意外变成全量请求。

## 2. 写入事务和幂等

一次逻辑写入的事务包含：检查幂等记录和版本前提、更新对应资源、增加对应 Event、保存原响应。提交后才回复成功，并提示订阅者。网络提示失败不回滚已经确认持久化的内容。

认证与授权先于幂等结果读取。幂等键作用域是稳定的令牌身份，允许的字符为 ASCII `!` 到 `~`，长度 1–128，不包含空格。令牌轮换后的重试不自动共享旧令牌的幂等记录。

请求摘要由方法、规范化资源路径、条件头、补齐默认值后的 JSON 构成。对象键递归按字典序排序，数组保持顺序；数字按 JSON 数值规范化，`1` 与 `1.0` 等价。相同键、相同摘要重放原响应；不同摘要返回 409。原响应包括状态码、JSON 正文、ETag、Location；Date 和请求跟踪 ID 可以重新生成。

幂等检查在当前版本检查之前。例如第一次带 `If-Match: "1"` 已写成版本 2，重试同一请求仍返回原成功结果，而非 412。默认保留成功记录 24 小时；校验与条件失败不保存幂等结果。并发相同键必须由数据库唯一约束和事务串行化，不能只靠内存检查。

Item 和 Notification 各自按事务顺序递增 revision。资源身份是 `(服务实例, topic_id, 资源类型, id)`，即使 ID 相同也互不影响。首次创建为 201，更新及恢复为 200。删除保留最后版本与最初 `created_at`，恢复后沿用二者；无条件删除不存在的条目返回 204，不生成事件。DELETE 不接受正文或 If-None-Match。

只有 PUT 可以使用 `If-None-Match: *`。PUT / DELETE 的 If-Match 只支持一个强整数 ETag，拒绝 `*`、弱 ETag 和列表；PUT 的两个条件头互斥。未提供条件时接受最后提交者覆盖。

`POST /v1/topics/{topic}/publish` 可以提交 item、notification 或两者，至少一部分。每部分显式传 id；省略的部分不变，不自动复制字段或创建关联。一次事务更新全部提交的资源，每部分各有版本和事件；任何条件失败都回滚全部写入与幂等记录。响应 200，仅含本次提交的资源。请求级条件头拒绝；每部分可带 if_revision，0 表示要求不存在，正数表示匹配当前版本，缺省无条件覆盖。请求中的 Idempotency-Key 覆盖整个组合操作。

## 3. 历史、删除与保留

每个成功的普通 PUT 留下一条完整版本事件；DELETE 仅在当前存在时留一条删除事件。Event 的主题、资源 ID、版本、记录时间必须与嵌入的 Item 或 Notification 对应；Event ID 由服务生成 UUID，不用它排序。

`item.deleted` 的 item 为 null，仅移除该展示条目及其小组件内容，不清除通知。`notification.cleared` 的 notification 为 null，仅清除该通知，不修改展示条目。两种删除均保留历史和版本墓碑，再发布同一 ID 可以恢复。清理历史不修改当前资源。对“今天一份日报”的业务，推荐每天一个 ID；持续状态用固定 ID。

每个主题最多 500 个当前展示条目和 500 个当前通知，分别计数。通知不占用展示条目额度；通知不再需要时可以主动清除，以释放通知额度。TTL 不释放额度，历史清理也不改变当前通知。

历史默认保留 30 天。清理只移除日志的连续旧前缀，并持久保存删除水位，不能在可恢复范围中间打洞。最旧保留序号之前的合法同步位置，只有等于删除水位时仍可继续，否则为 410。即使全部历史已清理，也保留最新日志位置与删除水位。

数据库重建或从备份回滚时更换日志世代；普通重启保留世代。旧世代同步游标返回 410。服务恢复流程必须执行世代更新，不能让旧游标被误认为已读过恢复后的新事件。

## 4. 同步必须保持一个完整的进度

无 cursor 的请求，在同一读事务中读取全部当前 Item、Notification 及对应高水位，返回快照。快照的 items 和 notifications 是分开的数组。手机用快照分别替换该主题两类当前内容，清除不在快照里的旧条目；日志世代变化时也不沿用旧版本比较结果。相关小组件与已有通知需要一起重新核对，快照不创建新提醒。

有 cursor 时，服务开始一轮增量同步，取本轮固定高水位。返回的游标携带最后已交付位置；如果仍有分页，也携带本轮高水位。每页只返回这一区间内的连续事件，按序号升序。最后一页 `has_more=false`，游标进入可开启下一轮的状态；期间新写入留给下一轮。

页数或字节数有限时宁可多分页，不能跳过中间事件。`has_more=true` 必须至少返回一条事件并推进游标。读取、判断保留水位和计算分页在同一读视图内完成，避免清理并发导致静默漏取。

游标需要完整性保护，例如服务持久密钥签发的 HMAC，包含类型、主题、世代和序号/分页上界；客户端将其视为不透明字符串。有效但过期的同步游标为 410，格式、签名、类型或主题错误为 400；游标从来不替代访问权限。

手机用同一个本地事务保存事件、两类当前资源、待通知标记和游标。展示操作随后执行，进程恢复后重试待展示标记。正常增量的删除要分别保留两类资源的本地最后版本，直到后续权威快照替换它，避免乱序内容将条目复活。

历史接口有独立分页游标：固定第一次读取的高水位、主题、筛选条件和下一页位置；item_id 与 notification_id 互斥，缺省返回两类事件。保持筛选条件，降序返回；不能把它用于 sync。历史清理导致旧记录消失是保留策略的一部分，历史页可以变短。世代变化或筛选不符返回 400，用户从首页重新浏览。

## 5. 提醒是展示动作，不是同步进度

一轮增量同步结束后，只处理 notification 事件，按 Notification ID 合并，**以最后一次事件为准**。最后一次是清除，则取消通知；最后一次是未过期 alert，才创建或更新一次通知。最后一次是 silent 或过期 alert，只能静默更新系统中仍存在的通知，不重新创建已被用户划掉的通知。

item 事件只更新展示条目，永不创建、刷新或清除系统通知。用户在系统里划掉通知是本地动作，不修改服务端当前 Notification，也不删除任何条目或历史。服务端 DELETE notification 则通过同步让客户端清除对应通知，并在服务端保留清除事件。

首次快照、游标失效后的快照和历史浏览不补弹旧提醒。快照用 notifications 核对已有通知：仍存在则静默更新，已不在快照中则清除。新快照之后的增量按正常规则处理。通知权限和用户偏好决定是否打扰；模板或素材下载不阻塞通知，也不产生新提醒。

Android 通知使用 `(主题, notification_id)` 的稳定身份，和小组件的 item_id 分开。当前使用系统的 onlyAlertOnce，仍在通知栏的同 ID 通知更新不重复发声；新 ID 表示另一条通知。重试处理减少重复，但不承诺跨进程崩溃窗口严格只展示一次。

SSE 只发送 `sync_required` 与注释心跳，无正文投递、无可恢复的 SSE 事件 ID。先注册订阅者，再发送首次提示；提交后提示可以合并。App 打开、SSE 首次连接和重连时都调用同一同步流程；前台每 60 秒检查可补偿漏掉的提示。后台执行机会由 Android 决定。

## 6. 权限和资源

读取、写入均限定到 Topic；管理员可执行全部操作。主题和模板资源由管理员配置。只有写入权限不代表可读取；有效读取令牌可以读取实例共享模板与素材。模板、素材不可放入密钥或私密业务正文。

模板发布前校验路径 id/version 与正文一致、引用素材存在、能力声明与实际组件一致、树大小和深度受限。相同版本相同规范化文档是安全重试，不同文档为 409。素材按字节哈希去重，重复上传也是安全重试。

令牌撤销后关闭相关 SSE 连接。手机收到明确 401/403 或用户移除订阅后，清理对应私有数据和展示。离线客户端在得知撤销前无法立刻获知远端变化，不把它表述为远程擦除能力。

所有响应新增可选字段时客户端应容忍，模板则按 renderer_version 和能力整体校验、必要时回退。服务写入端拒绝未定义字段，不解释业务 data 中的字符串为代码。

## 7. 从首轮 v0.1 升级

这次是开发期契约调整：原 Item 请求的 notify 字段被拒绝，调用方应改用独立通知接口或组合发布。数据库版本 1 → 2 自动保留原条目，把尚在历史中的旧提醒转为独立通知记录与事件；旧条目仍可用于原小组件。旧提醒的正文迁移时最多取 500 码点，原条目正文和历史内容完整保留。已被保留策略清理的历史不会凭空重建。迁移更换日志世代，旧游标返回 410。旧格式幂等请求不能跨此次契约变更重放，调用方需先确认当前状态再按新结构提交新的逻辑操作。

Android Room 版本 1 → 2 保留条目、小组件绑定、模板和设置，新增独立通知表，重置同步游标与历史缓存，从快照恢复，不补弹旧提醒。旧版客户端不支持新通知事件，应与服务端一同升级。
